# Журнал для оценки обучающихся — Лабораторная работа №3

Система «Журнал для оценки обучающихся» (вариант 2). Реализованы **задания 1–5** ЛР №3:

- **Задание 3 — Аутентификация и токены**: пароли Argon2id + соль + pepper; JWT (HS256) с отзывом через Redis; восстановление доступа через Mailpit.
- **Задание 4 — Эндпоинты по контракту ЛР №2**: оценки (чтение/изменение/список), заявки на пересдачу, подтверждение оценки сотрудником, курсы, аудит. Объектная авторизация, оптимистичная блокировка (version), аудит всех изменений, нейтральные 500, параметризованные запросы.

Технологии: **Python 3.12 + FastAPI**, **PostgreSQL 16**, **Redis 7**, **Mailpit** (стаб почты). Развёртывание — **Docker Compose** одной командой.

---

## 1. Требования к компьютеру

- Docker Engine + Docker Compose (v2). Проверка: `docker compose version`.
- Любая ОС, на которой работает Docker. Порты, используемые системой:

| Порт | Сервис | Назначение |
|---|---|---|
| 8000 | API (FastAPI) | REST API, Swagger: http://localhost:8000/docs |
| 5432 | PostgreSQL | База данных (наружу — для отладки) |
| 6379 | Redis | Стоки, лимиты, коды |
| 1025 / 8025 | Mailpit | SMTP стаб / веб-почта http://localhost:8025 |

---

## 2. Запуск и остановка

```bash
# 1) один раз: подготовить окружение из шаблона
cp .env.example .env
# при необходимости отредактируйте .env (обязательно: JWT_SECRET, PASSWORD_PEPPER)

# 2) собрать и поднять все контейнеры одной командой
docker compose up --build

# 3) остановить
docker compose down
```

После `docker compose up` база создаётся автоматически из `db/schema.sql`, создаётся роль приложения `app_api` из `db/roles.sql`, а тестовые пользователи заносятся приложением при старте (`api/app/seed.py`). **Ручных действий в базе не требуется.**

> Замечание по слою безопасности: приложение подключается к БД **только** под ролью `app_api`, у которой нет прав `CREATE/DROP` — с её учётной записью `DROP TABLE`/`CREATE TABLE` завершаются ошибкой прав (минимум привилегий, граница TB-03).

---

## 3. Тестовые учётные записи (по ролям)

Создаются автоматически при первом старте. Пароли хранятся в базе только в виде хэша (Argon2id + соль + pepper).

| Роль | Email | Пароль |
|---|---|---|
| Обучающийся (student) | `student@test.edu` | `Student!123` |
| Обучающийся №2 (student) | `student2@test.edu` | `Student2!123` |
| Преподаватель (teacher) | `teacher@test.edu` | `Teacher!123` |
| Сотрудник / администратор (employee) | `employee@test.edu` | `Employee!123` |

Два студента записаны на курс **CS-101** и имеют собственные оценки, чтобы на защите показать,
что один студент токеном другого не видит его оценки (объектная авторизация, задание 2.3/4).
Course CS-101 создаётся автоматически при старте (`api/app/seed.py`).

## 4. Сброс базы в исходное состояние

```bash
# остановить и удалить том данных, затем поднять заново
docker compose down -v
docker compose up --build
```

После этого база пересоздаётся из скриптов, а тестовые пользователи заносятся заново.

## 5. Проверка функциональности

1. Откройте Swagger: http://localhost:8000/docs
2. Выполните последовательность запросов из `requests/auth.http` (или запустите `.\requests\curl_checks.ps1`).
3. Письма с кодом восстановления — в веб-почте Mailpit: http://localhost:8025

Ключевые проверки задания 3:
- **Неверный email и неверный пароль** → одинаковый ответ `401 {"detail": "Неверный email или пароль"}`.
- **Просроченный/подделанный/отозванный токен** → `401`.
- **Выход из системы** → сессия удаляется из Redis, тот же токен снова даёт `401`.
- **Код восстановления** → действует 15 минут и только один раз.

## 7. Эндпоинты (таблица)

| Метод | Путь | Назначение | Контракт / Задание |
|---|---|---|---|
| POST | `/api/v1/auth/register` | Регистрация (роль ставит сервер) | 3.1 |
| POST | `/api/v1/auth/token` | Вход | O-07 / 3.1 |
| POST | `/api/v1/auth/logout` | Выход (отзыв токена) | 3.2 |
| GET | `/api/v1/auth/me` | Текущий пользователь | 3.2 |
| POST | `/api/v1/auth/password-reset/request` | Запрос кода восстановления | 3.3 |
| POST | `/api/v1/auth/password-reset/confirm` | Смена пароля по коду | 3.3 |
| GET | `/api/v1/grades/{id}` | Оценка по ID (студент — только своя) | O-01 / 4 |
| PATCH | `/api/v1/grades/{id}` | Изменить оценку (teacher/employee + version) | O-03 / 4 |
| GET | `/api/v1/grades?course_id=` | Список оценок (объём по правам) | O-04 / 4 |
| POST | `/api/v1/retake-requests` | Заявка на пересдачу (student) | O-02 / 4 |
| POST | `/api/v1/retake-requests/{id}/check` | LLM-проверка — стаб `501` | O-06 / 4 |
| GET | `/api/v1/courses/{id}` | Курс | O-08 / 4 |
| POST | `/api/v1/admin/grades/{id}/confirm` | Подтверждение оценки (employee) | O-05 / 4 |
| GET | `/api/v1/audit/events` | Журнал аудита (employee) | O-09 / 4 |

Секреты (JWT_SECRET, PASSWORD_PEPPER, пароль БД) никогда не хранятся в репозитории и не возвращаются клиенту.
Пароль-хэш не отдаётся ни одним эндпоинтом; системные поля (owner_id, student_id, actor_id, created_at) вычисляются сервером.

## 8. Ключевые проверки задания 4

1. **Чужая оценка**: студент `student@test.edu` токеном получает `GET /grades/{id}` оценки
   студента №2 → `404` (объект скрыт, а не `403`).
2. **Студент меняет оценку** `PATCH /grades/{id}` → `403` (RBAC).
3. **Лишние поля в теле** (owner_id / status / role) отбрасываются Pydantic-моделью запроса:
   владелец и статус в БД остаются серверными.
4. **Оптимистичная блокировка**: повторный `PATCH` со старым `version` → `409`.
5. **Повторная заявка на пересдачу** при уже активной `pending` → `409`.
6. **Подтверждение сотрудником** пишет запись в `audit_log`; она видна в `GET /audit/events`.
7. Непредвиденная ошибка → `500 {"detail":"Внутренняя ошибка сервера"}` (без стека и SQL).
