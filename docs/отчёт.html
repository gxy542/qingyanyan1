1. Цель и что сделано

Цель работы — реализовать и развернуть локально систему «Журнал для оценки обучающихся», спроектированную во второй работе. Контракты ЛР № 2 стали обработчиками, DDL — реальной базой данных, блок решений по безопасности — проверками в коде.

Выполнены все задания ЛР № 3:

  1. Проект и окружение: git-репозиторий, структура каталогов, docker-compose.yml, поднимающий систему одной командой, .env.example, README с инструкциями.
  2. База данных: PostgreSQL 16, схема из db/01_schema.sql разворачивается автоматически; приложение под отдельной ролью app_api без прав DDL; тестовые данные: два студента, преподаватель, сотрудник, курс CS-101 и оценки.
  3. Аутентификация и токены: регистрация/вход, Argon2id + соль + pepper, JWT (HS256) с отзывом через Redis, восстановление доступа одноразовым кодом в Mailpit.
  4. Эндпоинты по контракту: все операции ЛР № 2 (кроме LLM) реализованы; объектная авторизация, оптимистичная блокировка, аудит, параметризованные запросы, нейтральные 500.
  5. Межсервисное взаимодействие: PostgreSQL + Redis, заявленные в проекте; каждое взаимодействие идёт по контракту.
  6. Клиентское приложение: веб-клиент для студента (просмотр своих оценок, заявка на пересдачу) и для сотрудника/преподавателя (таблица оценок, изменение значения, подтверждение).
  7. Проверка и карта кода: коллекция запросов в requests/; три проверочных запроса (чужой объект, лишние поля, привилегированная операция) задокументированы в docs/проверочные_запросы.md.

5. Ключевые решения по безопасности

5.1 Пароли

Пароль хэшируется Argon2id со случайной солью и pepper из переменной окружения. Соль хранится в БД рядом с хэшем, pepper — только в окружении, в репозиторий не попадает. При неверном логине и при неверном пароле система отвечает одинаково.

5.2 Токены

JWT (HS256), ключ подписи читается из JWT_SECRET. В Redis хранится allowlist выданных токенов; logout и смена пароля немедленно удаляют токен из Redis — просроченный, подделанный и отозванный токены отклоняются с кодом 401.

5.3 Объектная авторизация

Обработчик GET /grades/{id} сначала читает запись, затем проверяет student_id текущего пользователя. Если чужой — возвращается 404, а не 403: нарушитель не узнаёт, существует ли такой объект.

5.4 Лишние поля в теле запроса

Pydantic-модели запросов не содержат системных полей (owner_id, student_id, status, role). Клиент не может «выдать» себе роль или чужого владельца. Имя владельца и статус записи вычисляются сервером.

5.5 Оптимистичная блокировка

PATCH /grades/{id} принимает текущую версию; обновление идёт с условием WHERE id=$1 AND version=$2. Если версия устарела — 409 Conflict. Это предотвращает гонку одновременных правок.

5.6 Аудит

Каждое изменение оценки и каждое подтверждение сотрудником пишется в таблицу audit_log (кто, что, когда, какое значение). Просмотреть журнал может сотрудник.

5.7 Нейтральные ошибки

Непредвиденное исключение перехватывается middleware и возвращает 500 {"detail": "Внутренняя ошибка сервера"}. Текст исключения, стек вызовов и SQL уходят только в лог контейнера. Все запросы к БД параметризованы.

5.8 Учётная запись приложения в БД

Сервис подключается под ролью app_api, а не под postgres. Скрипт db/02_roles.sql выдаёт только SELECT/INSERT/UPDATE/DELETE; DROP TABLE и CREATE TABLE под этой ролью завершаются ошибкой прав.

6. Три контрольных запроса (Задание 7.2)

6.1 Чужой объект с валидным токеном

GET /api/v1/grades/<id_оценки_студента_2>
Authorization: Bearer <токен_студента_1>
→ HTTP 404 {"detail":"Оценка не найдена"}

6.2 Лишние поля в теле запроса

PATCH /api/v1/grades/<своя_оценка>
{"value":99,"version":1,
 "owner_id":"<uuid_другого>","status":"closed","role":"employee"}
→ отброшено: владелец и статус в БД не изменены

6.3 Привилегированная операция токеном студента

POST /api/v1/admin/grades/<id>/confirm
Authorization: Bearer <токен_студента>
→ HTTP 403 {"detail":"Недостаточно прав"}
